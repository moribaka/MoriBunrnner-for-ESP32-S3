# v2.32.118 烧录优先，音乐让出资源

用户要求：烧录时必须暂停音乐，不能影响烧录；音量设置为1%，午睡期间不出声。

## 实现

- 公共卡带任务在创建工作任务和计算PSRAM窗口前获取音乐独占引用。
- ROM写入的公共TF入口在文件分析/补丁准备前获取引用，任务接手自己的引用，
  准备失败释放引用。没有修改卡带擦写算法、分块、空白判断、校验或频率。
- AG32 batch编程入口在载入文件之前同样获取引用，所有正常/错误收尾释放。
- 获取首个引用时保存音乐路径/时间，向Lyra发送停止请求，并等待音频任务
  确认已关闭输入/解码器、释放PCM/预读缓冲、结束I2S输出。
- 持有引用时，TF/SMB播放、恢复、快进均拒绝；同一适配器锁避免播放请求
  与资源交接交叉。引用归零不自动恢复，界面继续显示暂停，用户手动恢复原位置。
- 音乐固定的工作任务/驱动资源保留；释放的是本曲解码器、输入和动态播放缓冲。
  不宣称全部播放器常驻内存都被释放。
- 调音量仍可操作，初始已通过API保存1%，测试仅生成全零静音MP3。

## 验证

- `tests/audio_host/test_burn_priority.cpp` 编译真实音乐适配层，模型后端覆盖
  未初始化时占用、嵌套引用、阻止TF/SMB/暂停/快进、无自动续播、手动续播及停止。
- AG32生产实现18组故障/成功/快照用例通过，确认接管SWD前有音乐引用，
  所有失败和成功出口无泄漏。IDF构建与Web回归通过。
- app v2.32.118 已刷入COM26，MAC a4:cb:8f:f2:c4:c0，esptool哈希验证通过。
- 实机使用静音MP3+32MiB GBC只读dump测试，不擦写卡带、不更新AG32。
  日志显示7.834s音频退出并释放缓冲，7.848s计算PSRAM窗口（空闲约7.54MB），
  7.856s启动burn_task，7.871s初始化40MHz SPI。
- 随后HTTP无响应且COM26从系统消失，端口枚举仅剩另一设备COM19。
  无panic证据，未定位掉线原因。实机后续的播放拒绝、完成后暂停、手动恢复
  **未完成验证**，不能宣称整条实机回归通过。
